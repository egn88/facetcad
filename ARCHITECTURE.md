# Architecture — Ports and Adapters

## Dependency rule

Dependencies point **inwards only**. Nothing in an inner ring may import from an outer ring.

```
                 ┌─────────────────────────────────────────┐
                 │            adapters (outer)             │
                 │                                         │
   driving  ───► │  http/            mcp/                  │
                 │                                         │
                 │      ┌───────────────────────────┐      │
                 │      │      application          │      │
                 │      │  use cases + PORTS        │      │
                 │      │                           │      │
                 │      │   ┌───────────────────┐   │      │
                 │      │   │      domain       │   │      │
                 │      │   │  pure, zero deps  │   │      │
                 │      │   └───────────────────┘   │      │
                 │      └───────────────────────────┘      │
                 │                                         │
   driven   ◄─── │  geometry/occt   geometry/fake          │
                 │  persistence/filesystem   export/…      │
                 └─────────────────────────────────────────┘
```

| Ring | May import | Contains |
|---|---|---|
| `domain` | stdlib only | Entities, value objects, the tag algebra, selector semantics, expression evaluation |
| `application` | `domain` | Use cases, the recompute engine, and the **port protocols** |
| `adapters` | `application`, `domain` | OCCT, the fake kernel, filesystem persistence, FastAPI, exporters |

`domain` imports nothing but the standard library, and `application` imports nothing from
`adapters` — the OCP types appear in exactly one package. That rule is what keeps the
kernel swappable rather than merely nominally abstracted. It is held by review today: an
import-linter contract enforcing it in CI is an obvious gap and is not there yet.

## The ports

Ports are `typing.Protocol` classes — structural, so adapters never import a base class
and the dependency arrow stays pointing inwards (DIP).

### `GeometryKernel` — the primary driven port

```python
class GeometryKernel(Protocol):
    name: str
    capabilities: frozenset[str]
    def pad(self, request: PadRequest) -> SolidResult: ...
    def pocket(self, base: SolidHandle, request: PocketRequest) -> SolidResult: ...
    def fuse(self, base: SolidHandle, addition: SolidHandle) -> SolidResult: ...
    def tessellate(self, solid: SolidHandle, tolerance: float = 0.1) -> Tessellation: ...
    def bounding_box(self, solid: SolidHandle) -> BoundingBox: ...
    def release(self, solid: SolidHandle) -> None: ...
```

Everything beyond that floor is a separate protocol — `BlendKernel` (fillet, chamfer),
`ThreadKernel`, `ProfileExtractor` (flattening a face or a section to 2D) — so a kernel
that cannot blend is not forced to say so by raising.

The critical design point: **the kernel returns provenance, not just a shape.**

```python
@dataclass(frozen=True)
class SolidResult:
    solid: SolidHandle
    faces: tuple[FaceRecord, ...]     # each carries its provenance + fingerprint
    edges: tuple[EdgeRecord, ...]     # each named by the two faces it separates
    deleted: tuple[DeletedFace, ...]  # consumed input faces, with the reason
```

`deleted` is why a selector failure can say *"face `base/side[outline.left]` was consumed
by feature `slot_1`"* rather than just reporting a count that changed.

`FaceRecord.provenance` says *how this face came to exist* in kernel-neutral terms —
"generated by profile curve `out.left`", "modified from input face #3", "generated by the
cut tool's lateral surface". The kernel adapter does **not** invent names. Naming is a
domain concern: `domain.tags` turns provenance into a `FaceTag`. This split is what lets a
mesh kernel, a B-rep kernel, or the fake kernel all feed the same naming engine.

### Other ports

| Port | Purpose | Adapter |
|---|---|---|
| `DocumentRepository` | Load/save/list project documents | filesystem (YAML) |
| `SnapshotStore` | Keep built geometry between runs, by content hash | filesystem (binary) |
| `Warmer` | Prepare export-detail geometry before it is asked for | background thread + a second kernel |
| `MeshExporter` | STL (binary and ASCII), OBJ | OCCT, analytic |
| `BrepExporter` | STEP | OCCT only — `Capability` guarded |
| `DrawingExporter` | DXF / SVG, as planar sections | OCCT only — `Capability` guarded |
| `ProfileExtractor` | One face or one section, flattened to 2D curves | OCCT only — `Capability` guarded |
| `BlendKernel` | fillet, chamfer | OCCT only — `Capability` guarded |
| `ThreadKernel` | the cut helical form | OCCT only — `Capability` guarded |
| `SolidSnapshots` | Serialise a solid and restore it with the *same* refs | both — `Capability` guarded |

The drawing exporter takes sections rather than hidden-line projections on purpose: a
section is exactly the material present at that height, which is what a laser or a router
needs, and it cannot silently drop a feature the way a mis-tuned HLR pass can.

Not every kernel can do everything. Rather than fattening one interface (ISP violation)
or having adapters raise `NotImplementedError` (LSP violation), capabilities are declared:

```python
kernel.capabilities  # frozenset[str]  e.g. {PAD, POCKET, TESSELLATE, BREP_EXPORT}
```

Use cases check capability up front and fail with a clear domain error, so a kernel that
supports less is still a *substitutable* kernel.

## Why two geometry adapters from day one

`adapters/geometry/fake` is an analytic kernel that handles axis-aligned prismatic solids
exactly, in pure Python. It exists for three reasons:

1. **It proves the port is real.** A port with one implementation is a guess. Two force
   the abstraction to be honest, and any leak of OCCT concepts into `application` shows up
   immediately as a compile-time hole in the fake.
2. **Test speed.** With OCCT absent entirely, 809 of the 1112 backend tests still run — the
   naming, selector, recompute and snapshot suites, which are the ones that fail first when
   the tag algebra is wrong — and they finish in about fifteen seconds against the eighty-five
   the full suite takes. The parameter sweeps are among the 303 that drop
   out, deliberately: a stability proof has to run on the kernel that ships.
3. **Bisecting failures.** When a model misbehaves, running it against both kernels
   answers "is this our naming layer or the kernel?" in one command.

## SOLID, concretely

- **SRP** — `domain.tags` names; `application.recompute` schedules; the kernel adapter does
  geometry. The engine never touches OCCT types; the adapter never invents a tag.
- **OCP** — new feature types (hole, fillet, revolve) register a `FeatureHandler` into a
  registry. Adding one touches no existing handler and no `if feature.type == …` chain.
- **LSP** — `Capability` sets instead of methods that raise. Both kernel adapters pass the
  identical port conformance suite.
- **ISP** — `MeshExporter`, `BrepExporter` and `DrawingExporter` are separate ports. A
  mesh-only kernel implements one and is not forced to stub the others.
- **DIP** — `application` depends on `Protocol` definitions it owns; adapters are injected
  by a composition root in `main.py`. There is exactly one place in the codebase that
  knows both OCCT and FastAPI exist.

## Bodies and the recompute unit

The recompute engine's unit of work is a **body**, not a document. Each body owns a
linear feature history and rebuilds independently:

```python
RecomputeResult.bodies  # tuple[BodyResult, ...] — solid, outcomes, placement, error
```

Two consequences worth stating explicitly:

- **The cache key is namespaced by body and detail level**
  (`f"{detail}/{body.id}/{spec.id}"`). Two bodies may legitimately hold features with the
  same id; without the namespace one would serve the other's cached solid. Detail belongs
  in the key for the same reason: a thread declared `modelled: "export"` is a different
  solid on screen and in the file.
- **A failing body does not take the document down.** Its `BodyResult.error` is
  reported and the rest still build, so the viewport keeps showing the parts that are
  fine — the same fail-loud-but-locally principle selectors follow.

`Body.placement` is resolved to a `Frame` and handed to the viewport and the exporters
as a transform. It is deliberately *not* baked into the modelled shape: canonical
ordinals and fingerprints are computed in the owning feature's local frame, and moving
a body must not be able to reach them.

### Copies fall out of that separation

A body whose `of` names another is a **copy**: no history of its own, the source's solid
under its own id and placement. The engine builds the sources first, then emits each copy
as a `BodyResult` carrying the source's `solid` and `key`:

```python
BodyResult(id="leg_2", solid=source.solid, key=source.key, of="leg", placement=frame)
```

Two things make this nearly free rather than merely convenient, and both are consequences
of decisions already made for other reasons:

- **The cache key is content-addressed, not body-addressed.** Only the cache *slot* is
  namespaced by body; `_cache_key` hashes the spec, the upstream key and the parameters.
  A copy sharing the source's key therefore shares its cached mesh — `_tessellate` keys on
  `body.key` — so a document with twelve of a part tessellates one.
- **Placement was never in the geometry.** A copy differs from its source by a transform
  and nothing else, so there is no fingerprint or ordinal it could perturb.

The dividing line downstream is between surfaces that describe *the model* and surfaces
that describe *a part*. Copies are in the first and out of the second:

| surface | copies |
|---|---|
| viewport meshes, `/state`, `/bodies`, whole-model STL/OBJ | included, each at its placement |
| `topologies()`, selector resolution, flatten, views, cut paths, STEP | excluded |

Excluding them from `topologies()` is the load-bearing one. A copy introduces no name — it
shows the source's faces elsewhere — so listing it would report every tag once per copy and
turn the cross-body diagnostic ("that tag exists, but in body X") into noise. Selectors are
written against a history, and a copy has none. Asking `topology?body=leg_2` is answered
with a redirect to `leg` rather than an empty index, since the faces do exist.

`RecomputeResult.parts` is the piece count — each body that builds itself, with how many
times it appears. A copy reports `quantity == 0` so the quantities sum to the piece count
rather than doubling it.

## Feature handler registry (OCP in practice)

```python
@register
class PadHandler:
    @property
    def type(self) -> str: return "pad"
    @property
    def required_capability(self) -> str: return Capability.PAD
    def build(self, spec: FeatureSpec, ctx: BuildContext) -> FeatureBuild: ...
```

The registry holds six handlers today — `pad`, `pocket`, `hole`, `thread`, `fillet`,
`chamfer` — and `GET /api/feature-types` reports them, so a client never has to guess.
One handler may return several builds: a counterbored hole is a bore and then a wider,
shallower cut, one entry in the history and two kernel operations.

`ctx` gives the handler resolved parameters, the selector resolver, and the kernel port —
nothing else. A handler cannot reach the repository or the HTTP layer, so features stay
pure functions of (document, upstream shape).
